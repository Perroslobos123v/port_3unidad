Política institucional de respaldo y retención

DOCUMENTO

1.1 Propósito y alcance

Esta política establece cómo, cuándo y dónde se respalda la base de datos GradosTitulos, cómo se verifican las copias y por cuánto tiempo se conservan. Aplica a todas las copias completas, diferenciales y de registro (bitácora) generadas por el área de tecnologías de la información. Su finalidad es que el administrador deje de ejecutar respaldos manuales y que siempre pueda identificar cuál es el respaldo vigente y cuáles pueden eliminarse sin afectar la recuperación.

1.2 Análisis de volumen y tablas críticas

El crecimiento semestral (estudiantes, matrículas, trámites, pagos, evaluaciones, resoluciones y diplomas) se estima con el tamaño de la base y el número de filas por esquema. Las tablas de los esquemas Tramite, Documento y Seguridad son las más críticas para los procesos de grados y títulos.

T-SQL
USE GradosTitulos;
GO
EXEC sp_spaceused;
GO
SELECT s.name AS Esquema, t.name AS Tabla, SUM(p.rows) AS Filas
FROM sys.tables t
INNER JOIN sys.schemas s ON t.schema_id = s.schema_id
INNER JOIN sys.partitions p ON p.object_id = t.object_id AND p.index_id IN (0,1)
GROUP BY s.name, t.name
ORDER BY Filas DESC;
GO

1.4 Reglas de mantenimiento

Clasificación

  • Carpeta por base de datos y tipo.
  • Nombre con fecha y hora.
  • Extensión .bak (.trn para el log).

Retención segura

  • Nunca borrar el último completo.
  • No borrar diferenciales cuyo completo base siga vigente.
  • Registrar cada limpieza en la bitácora.

Estructura y nomenclatura

RUTA
C:\Backups\<BaseDatos>\<TIPO>\<BaseDatos>_<TIPO>_AAAAMMDD_HHMM.bak
Ejemplo: C:\Backups\GradosTitulos\FULL\GradosTitulos_FULL_20261122_0200.bak

El programador dispara usp_Backup; el procedimiento crea la carpeta, genera el archivo, lo verifica y registra el resultado (OK o ERROR) en la bitácora. 3.2 Procedimiento usp_Backup

Un único procedimiento realiza el respaldo FULL, DIFF o LOG, lo verifica con CHECKSUM y registra el resultado. Si ocurre un error, lo guarda en la bitácora y lo relanza con THROW para que el trabajo programado figure como fallido.

T-SQL
USE DBA_Admin;
GO
CREATE OR ALTER PROCEDURE dbo.usp_Backup
    @Base SYSNAME = 'GradosTitulos', @Tipo VARCHAR(4)
AS
BEGIN
    SET NOCOUNT ON;
    DECLARE @dir NVARCHAR(300) = N'C:\Backups\' + @Base + N'\' + @Tipo;
    DECLARE @arch NVARCHAR(400) = @dir + N'\' + @Base + N'_' + @Tipo + N'_'
        + FORMAT(GETDATE(),'yyyyMMdd_HHmm') + CASE WHEN @Tipo = 'LOG' THEN N'.trn' ELSE N'.bak' END;
    BEGIN TRY
        EXEC master.dbo.xp_create_subdir @dir;
        IF @Tipo = 'FULL'
            BACKUP DATABASE @Base TO DISK = @arch WITH CHECKSUM, COMPRESSION;
        ELSE IF @Tipo = 'DIFF'
            BACKUP DATABASE @Base TO DISK = @arch WITH DIFFERENTIAL, CHECKSUM, COMPRESSION;
        ELSE IF @Tipo = 'LOG'
            BACKUP LOG @Base TO DISK = @arch WITH CHECKSUM, COMPRESSION;
        RESTORE VERIFYONLY FROM DISK = @arch WITH CHECKSUM;
        INSERT dbo.BitacoraBackup (BaseDatos, Tipo, Archivo, Resultado)
            VALUES (@Base, @Tipo, @arch, 'OK');
    END TRY
    BEGIN CATCH
        INSERT dbo.BitacoraBackup (BaseDatos, Tipo, Archivo, Resultado, Mensaje)
            VALUES (@Base, @Tipo, @arch, 'ERROR', ERROR_MESSAGE());
        THROW;
    END CATCH
END;
GO
EXEC DBA_Admin.dbo.usp_Backup @Tipo = 'FULL';
EXEC DBA_Admin.dbo.usp_Backup @Tipo = 'DIFF';
SELECT * FROM DBA_Admin.dbo.BitacoraBackup ORDER BY Id DESC;

Procedimientos de verificación

T-SQL

usp_VerificarBackups revisa los respaldos de los últimos 8 días registrados en msdb y clasifica cada archivo: FALTA ARCHIVO (no existe en disco), DANADO (is_damaged), SIN CHECKSUM o OK. Así se detectan respaldos incompletos, inexistentes o que no cumplen la política.

T-SQL
USE DBA_Admin;
GO
CREATE OR ALTER PROCEDURE dbo.usp_VerificarBackups @Base SYSNAME = 'GradosTitulos'
AS
BEGIN
    SET NOCOUNT ON;
    CREATE TABLE #b (Archivo NVARCHAR(400), Tipo CHAR(1), Fin DATETIME,
                     Danado BIT, TieneChecksum BIT, Existe INT DEFAULT 0);
    INSERT #b (Archivo, Tipo, Fin, Danado, TieneChecksum)
    SELECT m.physical_device_name, b.type, b.backup_finish_date, b.is_damaged, b.has_backup_checksums
    FROM msdb.dbo.backupset b
    INNER JOIN msdb.dbo.backupmediafamily m ON b.media_set_id = m.media_set_id
    WHERE b.database_name = @Base AND b.backup_finish_date >= DATEADD(DAY, -8, GETDATE());
    DECLARE @a NVARCHAR(400), @e INT;
    DECLARE c CURSOR FOR SELECT Archivo FROM #b;
    OPEN c; FETCH NEXT FROM c INTO @a;
    WHILE @@FETCH_STATUS = 0
    BEGIN
        EXEC master.dbo.xp_fileexist @a, @e OUTPUT;
        UPDATE #b SET Existe = @e WHERE Archivo = @a;
        FETCH NEXT FROM c INTO @a;
    END
    CLOSE c; DEALLOCATE c;
    SELECT Archivo, Tipo, Fin,
           CASE WHEN Existe = 0 THEN 'FALTA ARCHIVO' WHEN Danado = 1 THEN 'DANADO'
                WHEN TieneChecksum = 0 THEN 'SIN CHECKSUM' ELSE 'OK' END AS Estado
    FROM #b ORDER BY Fin DESC;
END;
GO
EXEC dbo.usp_VerificarBackups;

Procedimiento de mantenimiento y retención

T-SQL

usp_Retencion elimina los archivos más antiguos que 35 días (completos) y 14 días (diferenciales). Antes de borrar comprueba que exista un completo vigente; si no existe, omite la limpieza y lo registra, de modo que nunca se queda la base sin una cadena de recuperación.

T-SQL
CREATE OR ALTER PROCEDURE dbo.usp_Retencion @DiasFull INT = 35, @DiasDiff INT = 14
AS
BEGIN
    SET NOCOUNT ON;
    DECLARE @cFull DATETIME = DATEADD(DAY, -@DiasFull, GETDATE());
    DECLARE @cDiff DATETIME = DATEADD(DAY, -@DiasDiff, GETDATE());
    -- Seguridad: no limpiar si no existe un completo vigente
    IF NOT EXISTS (SELECT 1 FROM msdb.dbo.backupset
                   WHERE database_name = 'GradosTitulos' AND type = 'D'
                     AND backup_finish_date >= @cDiff)
    BEGIN
        INSERT dbo.BitacoraBackup (BaseDatos, Tipo, Resultado, Mensaje)
            VALUES ('GradosTitulos', 'RETENCION', 'OMITIDO', N'No hay completo vigente');
        RETURN;
    END
    EXEC master.dbo.xp_delete_file 0, N'C:\Backups\GradosTitulos\DIFF', N'bak', @cDiff, 0;
    EXEC master.dbo.xp_delete_file 0, N'C:\Backups\GradosTitulos\FULL', N'bak', @cFull, 0;
    INSERT dbo.BitacoraBackup (BaseDatos, Tipo, Resultado)
        VALUES ('GradosTitulos', 'RETENCION', 'OK');
END;
GO
EXEC dbo.usp_Retencion @DiasFull = 35, @DiasDiff = 14;

✔Cómo demostrar la retención sin borrar respaldos reales

Con archivos recién creados, usp_Retencion no elimina nada (ninguno supera 35 ni 14 días). Para tener un «antes y después» seguro: copia un .bak a una carpeta de prueba (por ejemplo C:\Backups\Lab\Retencion), cámbiale la fecha de modificación con PowerShell a hace 20 días y borra con xp_delete_file solo en esa carpeta usando 14 días como límite. Así se ve que el archivo vencido desaparece y el reciente se conserva.

POWERSHELL + SQL
(Get-Item "C:\Backups\Lab\Retencion\viejo.bak").LastWriteTime = (Get-Date).AddDays(-20)
DECLARE @c DATETIME = DATEADD(DAY, -14, GETDATE());
EXEC master.dbo.xp_delete_file 0, N'C:\Backups\Lab\Retencion', N'bak', @c, 0;
EXEC master.sys.xp_dirtree N'C:\Backups\Lab\Retencion', 1, 1;

Simulación de fallos y detección

ESCENARIO 3

✖Cuidado

Daña solo una COPIA del archivo, nunca el respaldo original.

T-SQL
-- Fallo 1: base inexistente (debe quedar ERROR en la bitácora)
EXEC DBA_Admin.dbo.usp_Backup @Base = 'BaseInexistente', @Tipo = 'FULL';
SELECT TOP (3) * FROM DBA_Admin.dbo.BitacoraBackup ORDER BY Id DESC;
GO
-- Fallo 2: archivo dañado. Copia un .bak, trunca la COPIA y verifica:
RESTORE VERIFYONLY FROM DISK = N'C:\Backups\Lab\copia_danada.bak' WITH CHECKSUM;

Para preparar la copia dañada (PowerShell): se copia un respaldo a la carpeta Lab y se recorta el archivo a la mitad.

POWERSHELL
Copy-Item "C:\Backups\GradosTitulos\FULL\GradosTitulos_FULL_AAAAMMDD_HHMM.bak" `
          "C:\Backups\Lab\copia_danada.bak"
$f = [System.IO.File]::Open("C:\Backups\Lab\copia_danada.bak",'Open','ReadWrite')
$f.SetLength([int64]($f.Length / 2)); $f.Close()

La ejecución de usp_Backup con una base inexistente falla; el bloque CATCH guarda el error en la bitácora y lo relanza. El RESTORE VERIFYONLY sobre el archivo recortado también falla, lo que demuestra que un respaldo incompleto se detecta antes de necesitarlo.

RESULTADO

El administrador ya no ejecuta respaldos a mano: el sistema respalda, verifica, deja registro y limpia sin tocar las copias necesarias para recuperar.

Conclusiones

  • La automatización con trabajos programados elimina la dependencia de la ejecución manual y reduce el error humano.
  • La bitácora centraliza el resultado de cada respaldo, y la verificación detecta archivos faltantes, dañados o sin CHECKSUM.
  • La retención con guarda de seguridad evita borrar el último completo o los diferenciales que aún dependen de él.
  • La restauración periódica en un entorno de prueba es la única forma de confirmar que los respaldos realmente sirven.
