iObjetivo del proyecto

Implementar una estrategia de respaldo y recuperación punto en el tiempo de GradosTitulos mediante backups completos, diferenciales y de log, y restauración secuencial, para minimizar la pérdida de información ante errores operativos.

✖Situación problemática

Un usuario con permisos de modificación alteró trámites, pagos y evaluaciones. El error se detectó horas después, cuando ya había nuevas operaciones válidas. Se necesita volver a un instante anterior al error conservando lo válido.

1

Estrategia y política de respaldo

DOCUMENTO

1.1 Contexto y necesidad

La oficina de Grados y Títulos procesa a diario expedientes, pagos, evaluaciones, designaciones de asesores y jurados, resoluciones y emisión de diplomas. Perder una jornada de trabajo generaría retrasos administrativos y problemas con los estudiantes. Un respaldo completo o diferencial solo permite volver al momento en que se tomó la copia; cuando el error se descubre horas después, se pierde todo lo válido hecho entre la copia y el error. La solución es registrar cada transacción con backups del log y restaurar hasta un instante anterior al incidente.

1.2 Operaciones que requieren protección rigurosa

Esquema / tablaOperación transaccionalImpacto de perderla
Tramite.TramiteRegistro y avance de expedientesRetrasa grados y títulos
Tramite.PagoRegistro de pagos de derechosProblemas económicos y con estudiantes
Tramite.TrabajoInvestigacionTrabajos de investigación y planes de tesisPérdida de avance académico
EvaluacionEvaluaciones, sustentaciones, juradosInvalida actas y calificaciones
DocumentoResoluciones y diplomasDocumentos oficiales comprometidos

1.3 Conceptos clave

Cadena de recuperación

  • Completo + diferencial + logs.
  • Sin saltar ningún log.
  • Orden cronológico.

Modelo FULL

  • Necesario para BACKUP LOG.
  • Permite STOPAT.
  • Requiere logs periódicos.

STOPAT

  • Detiene la restauración en un instante.
  • Se usa en el último RESTORE LOG.
  • El resto: NORECOVERY.

1.4 Política de respaldo propuesta

TipoFrecuenciaHorarioRetención
CompletoSemanal (domingo)02:005 semanas
DiferencialDiario02:002 semanas
Log de transaccionesCada 15 minutosTodo el día7 días

El log cada 15 minutos limita la pérdida potencial a 15 minutos de actividad, adecuado para trámites y pagos (se analiza en el Entregable 7). Los archivos .trn deben copiarse también fuera del servidor: si se pierde un solo log de la cadena, no es posible restaurar más allá de ese punto.

EVIDENCIA 1Modelo de recuperación FULL verificado

2.2 Base de laboratorio con cadena propia

T-SQL
-- Base de laboratorio con cadena propia
EXEC master.dbo.xp_create_subdir N'C:\Backups\PITR';
BACKUP DATABASE GradosTitulos TO DISK = N'C:\Backups\PITR\Origen.bak'
WITH COPY_ONLY, CHECKSUM, INIT;
GO
-- Nombres lógicos de los archivos del respaldo (para WITH MOVE)
RESTORE FILELISTONLY FROM DISK = N'C:\Backups\PITR\Origen.bak';
GO
RESTORE DATABASE GradosTitulos_PITR FROM DISK = N'C:\Backups\PITR\Origen.bak'
WITH MOVE N'<LogicalNameDatos>' TO N'C:\Backups\PITR\PITR.mdf',
     MOVE N'<LogicalNameLog>'   TO N'C:\Backups\PITR\PITR_log.ldf', RECOVERY;
ALTER DATABASE GradosTitulos_PITR SET RECOVERY FULL;
GO

!Ajuste técnico recomendado: COPY_ONLY

Se agregó COPY_ONLY al backup Origen.bak. Un completo normal reinicia la base del diferencial de GradosTitulos; si se hiciera sin COPY_ONLY, los diferenciales del Proyecto 1 dejarían de poder restaurarse con el completo semanal. COPY_ONLY crea una copia independiente que no altera la cadena oficial.

iNota sobre GradosTitulos

Al cambiar GradosTitulos a FULL, el registro de transacciones solo empieza a conservarse después de un respaldo completo normal (no COPY_ONLY). Para hacer backups del log de la base real (Proyecto 4), realiza antes el backup completo del Proyecto 1. GradosTitulos_PITR no tiene este problema porque su cadena empieza con PITR_FULL.bak (Entregable 3).

3

Scripts de backup: completo, diferencial y log

T-SQL

Se construye la cadena en este orden: completo, lote 1 de datos válidos, diferencial, lote 2, primer backup del log. Cada lote queda registrado con su hora en una tabla de pruebas.

T-SQL
USE master;
GO
BACKUP DATABASE GradosTitulos_PITR TO DISK = N'C:\Backups\PITR\PITR_FULL.bak'
WITH CHECKSUM, COMPRESSION, INIT, STATS = 10;
GO
USE GradosTitulos_PITR;
GO
-- Tabla de pruebas con hora de cada operación
CREATE TABLE dbo.PruebaPITR (
    Id        INT IDENTITY PRIMARY KEY,
    Detalle   NVARCHAR(100) NOT NULL,
    FechaHora DATETIME2(3) NOT NULL DEFAULT SYSDATETIME()
);
INSERT dbo.PruebaPITR (Detalle) VALUES (N'Trámite válido 1'), (N'Pago válido 1'); -- lote 1
GO
BACKUP DATABASE GradosTitulos_PITR TO DISK = N'C:\Backups\PITR\PITR_DIFF.bak'
WITH DIFFERENTIAL, CHECKSUM, COMPRESSION, INIT, STATS = 10;
GO
USE GradosTitulos_PITR;
INSERT dbo.PruebaPITR (Detalle) VALUES (N'Evaluación válida 1'), (N'Pago válido 2'); -- lote 2
GO
BACKUP LOG GradosTitulos_PITR TO DISK = N'C:\Backups\PITR\PITR_LOG1.trn'
WITH CHECKSUM, COMPRESSION, INIT, STATS = 10;
GO
EVIDENCIA 2Backups FULL, DIFF y LOG1 ejecutados
4

Simulación del incidente

ESCENARIOS 1 Y 2

Se inserta un tercer lote todavía válido, se registra el instante anterior al incidente y, tras una espera de 5 segundos, se simulan el error operativo (eliminación de pagos y alteración de datos) y el segundo backup del log, que ya incluye el error.

T-SQL
USE GradosTitulos_PITR;
GO
INSERT dbo.PruebaPITR (Detalle) VALUES (N'Trámite válido 3'); -- lote 3 (todavía válido)
GO
-- Registrar el instante anterior al incidente y ANOTARLO
SELECT CONVERT(VARCHAR(23), SYSDATETIME(), 121) AS MomentoAntesDelIncidente;
WAITFOR DELAY '00:00:05';
GO
-- INCIDENTE (solo en el laboratorio)
DELETE TOP (10) FROM Tramite.Pago;
UPDATE dbo.PruebaPITR SET Detalle = N'DATO ALTERADO';
GO
BACKUP LOG GradosTitulos_PITR TO DISK = N'C:\Backups\PITR\PITR_LOG2.trn'
WITH CHECKSUM, COMPRESSION, INIT, STATS = 10;
GO

✖Importante

Ejecuta el SELECT del instante y anótalo de inmediato (el dato es la base del STOPAT). El WAITFOR y el incidente deben ejecutarse después de esa captura, sin demora excesiva.

5

Script de restauración secuencial con STOPAT

T-SQL · ESCENARIOS 3 Y 4
T-SQL
USE master;
GO
RESTORE DATABASE GradosTitulos_PITR_Rest FROM DISK = N'C:\Backups\PITR\PITR_FULL.bak'
WITH MOVE N'<LogicalNameDatos>' TO N'C:\Backups\PITR\Rest.mdf',
     MOVE N'<LogicalNameLog>'   TO N'C:\Backups\PITR\Rest_log.ldf',
     NORECOVERY, REPLACE;
RESTORE DATABASE GradosTitulos_PITR_Rest FROM DISK = N'C:\Backups\PITR\PITR_DIFF.bak'
WITH NORECOVERY;
RESTORE LOG GradosTitulos_PITR_Rest FROM DISK = N'C:\Backups\PITR\PITR_LOG1.trn'
WITH NORECOVERY;
RESTORE LOG GradosTitulos_PITR_Rest FROM DISK = N'C:\Backups\PITR\PITR_LOG2.trn'
WITH STOPAT = 'AAAA-MM-DD HH:MM:SS', RECOVERY;
GO

!Cómo elegir el STOPAT

Usa un instante algo posterior al anotado y anterior al incidente (los 5 segundos del WAITFOR sirven de margen). Ejemplo: si anotaste 14:32:10.123, usa STOPAT = '2026-11-21 14:32:12'. Debe estar en la misma zona horaria del servidor. Si el STOPAT queda antes del fin del backup del log, la base se recupera sin errores.

EVIDENCIA 5Restauración secuencial completada con STOPAT

Procedimiento documentado de recuperación punto en el tiempo

PasoAcciónDetalle
1Detectar y delimitarConfirmar qué operación causó el error y estimar la hora en que ocurrió.
2ContenerSuspender las escrituras sobre la base afectada para no ampliar el daño.
3Respaldar el final del logSi el servidor responde, tomar un backup del log (tail-log) para no perder las últimas transacciones.
4Reunir la cadenaÚltimo completo, último diferencial posterior y todos los logs en orden cronológico, sin faltantes.
5Definir el instanteFijar el STOPAT inmediatamente anterior al error, con margen de seguridad.
6Restaurar secuencialmenteFULL con NORECOVERY, DIFF con NORECOVERY, cada LOG con NORECOVERY y el último con STOPAT y RECOVERY.
7VerificarComparar registros válidos, descartar filas alteradas y ejecutar DBCC CHECKDB.
8Reabrir y documentarPoner la base a disposición de los usuarios y registrar tiempos y lecciones aprendidas.

Informe de análisis de pérdida potencial de datos

ESCENARIO 6

7.1 Impacto de la frecuencia del backup del log

La pérdida máxima ante un desastre que impida acceder al log activo es igual al intervalo entre backups del log. La cantidad de archivos por día se calcula como 1 440 minutos dividido entre el intervalo.

Frecuencia del logPérdida máximaArchivos por díaObservación
Cada 60 minHasta 60 min24Pocos archivos, mayor pérdida
Cada 30 minHasta 30 min48Equilibrio razonable
Cada 15 minHasta 15 min96Recomendada para trámites y pagos
Cada 5 minHasta 5 min288Mínima pérdida, más archivos a administrar

7.2 Medición de la recuperación

Para el tiempo de recuperación, anota la hora justo antes de iniciar la secuencia de restauración y justo al terminar:

T-SQL
SELECT SYSDATETIME() AS InicioRecuperacion;   -- antes del primer RESTORE
-- ... secuencia de restauración ...
SELECT SYSDATETIME() AS FinRecuperacion;      -- después del último RESTORE
ConceptoValor medido
Transacciones válidas recuperadas5 registros de los lotes 1, 2 y 3 en PruebaPITR y 120 pagos intactos
Transacciones perdidas por el incidente10 pagos eliminados y 2 filas alteradas (descartados con el STOPAT)
Tiempo total de recuperación

iGuía de lectura

Las transacciones válidas recuperadas son los registros de los lotes 1, 2 y 3 (5 filas en PruebaPITR) más los pagos intactos; las perdidas por el incidente son los cambios hechos por el error (10 pagos eliminados y las filas alteradas), que precisamente se descartan con el STOPAT.

Limitaciones del procedimiento

  • Se pierde lo ocurrido después del instante elegido.
  • Un log faltante rompe la cadena.
  • Exige modelo FULL desde antes del incidente.

Mejoras propuestas

  • Logs cada 15 minutos.
  • Copia externa de los .trn.
  • Pruebas de restauración periódicas.

08 Secuencia de restauración

Orden

  • 1. FULL → NORECOVERY
  • 2. DIFF → NORECOVERY
  • 3. LOG 1 → NORECOVERY
  • 4. LOG 2 → STOPAT + RECOVERY

Por qué funciona

  • El log guarda cada transacción.
  • STOPAT corta antes del error.
  • Se conserva todo lo válido.

RESULTADO

La base se recupera al instante anterior al incidente. La pérdida potencial es del tamaño del intervalo entre backups del log.

09 Dificultades encontradasdocumenta cada problema y su solución

N.ºDificultadSolución aplicada
1Elegir el instante exacto para el STOPAT, de modo que quedara antes del incidente y después del último dato válido.Se anotó el instante 14:32:10.123 antes del incidente y se usó STOPAT = 14:32:12, aprovechando los 5 segundos del WAITFOR como margen.
2Mantener la cadena de restauración completa y en orden.Se restauró FULL, DIFF y LOG1 con NORECOVERY, y el LOG2 con STOPAT y RECOVERY, sin saltar ningún archivo.
3Comprobar que se recuperó solo lo válido y sin dañar la base original.Se trabajó en GradosTitulos_PITR y se verificó con el conteo de pagos (90 con incidente, 120 recuperados) y DBCC CHECKDB sin errores.

Conclusiones

  • El modelo FULL y los backups del log permiten recuperar con precisión de minutos, algo imposible con completo y diferencial solos.
  • STOPAT en el último RESTORE LOG detiene la recuperación justo antes del error y conserva las transacciones válidas.
  • La cadena debe estar completa y en orden: un log faltante impide restaurar más allá de ese punto.
  • La frecuencia del log define la pérdida máxima; 15 minutos es un equilibrio razonable para trámites y pagos.
