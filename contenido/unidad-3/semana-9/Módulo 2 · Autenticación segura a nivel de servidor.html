Fundamento teórico Autenticación = verificar la identidad

a) Autenticación de Windows

  • Usa credenciales de Windows o Active Directory.
  • Integra la seguridad del sistema operativo.
  • Administra usuarios mediante grupos de Windows.
  • Evita contraseñas independientes en SQL Server.
  • Recomendada en entornos corporativos con dominio.

b) Autenticación de SQL Server

  • Crea cuentas (Logins) directamente en el motor.
  • Administra credenciales propias de SQL Server.
  • Facilita aplicaciones que requieren autenticación SQL.
  • Exige políticas estrictas de contraseñas.

c) Autenticación mixta (Mixed Mode)

  • Permite usar a la vez Windows y SQL Server.
  • Se habilita en este laboratorio para crear un usuario específico que acceda al proyecto analítico.

ACTIVIDAD1

Habilitar el modo de autenticación mixta

SSMS
  1. Abre SQL Server Management Studio.
  2. Conéctate al servidor mediante autenticación de Windows.
  3. En el Explorador de objetos, clic derecho sobre el nombre del servidor.
  4. Selecciona Properties.
  5. Ingresa a la sección Security.
  1. Localiza Server authentication. Verás dos alternativas: Windows Authentication mode y SQL Server and Windows Authentication mode.
  2. Selecciona: SQL Server and Windows Authentication mode.
  3. Presiona OK.
  4. Reinicia el servicio: abre SQL Server Configuration Manager > SQL Server Services > SQL Server (MSSQLSERVER) > clic derecho > Restart.

!Importante

El cambio del modo de autenticación requiere reiniciar el servicio del motor. No es suficiente cerrar y volver a abrir SSMS.

ACTIVIDAD2

Crear un inicio de sesión con políticas de seguridad (interfaz gráfica)

SSMS

Se creará el login analista_upla, destinado a consultar información de la base de datos del proyecto analítico.

  1. Abre SSMS y conéctate al servidor.
  2. Expande el nodo Security > Logins.
  3. Clic derecho sobre Logins.
  4. Selecciona New Login.
  5. En Login name escribe: analista_upla
  6. Selecciona SQL Server authentication.
  7. Ingresa una contraseña robusta definida para el laboratorio. Ejemplo de formato: Upla_Analitica#2026_Lab!

!Contraseña demostrativa

Es exclusivamente demostrativa. En una implementación real debe generarse una contraseña única, aleatoria y no reutilizada.

  1. Activa: Enforce password policy y Enforce password expiration.
  2. Desactiva User must change password at next login solo si es una cuenta técnica administrada mediante un procedimiento seguro de entrega de credenciales.

iEn producción

Las cuentas de aplicaciones deben gestionarse con una política de rotación y almacenamiento seguro de secretos, sin distribuir contraseñas manualmente.

  1. Ingresa a Server Roles y verifica que NO esté seleccionado el rol sysadmin.
  2. Ingresa a User Mapping y selecciona la base de datos ProyectoAnalitico_UPLA.
  3. Los permisos de acceso a la base de datos se asignan mediante T-SQL en las siguientes actividades.
  4. Presiona OK.
ACTIVIDAD3

Crear el login utilizando T-SQL

Nueva consulta en SSMS

Para comprender la administración de cuentas a nivel de servidor, ejecuta el siguiente script con una cuenta administradora autorizada.

  1. Abre una nueva ventana de consulta en SSMS.
  2. Ejecuta el siguiente código:
T-SQL
USE master;
GO

-- Crear el inicio de sesión SQL Server
CREATE LOGIN analista_upla
WITH
    PASSWORD = 'Upla_Analitica#2026_Lab!',
    CHECK_POLICY = ON,
    CHECK_EXPIRATION = ON,
    DEFAULT_DATABASE = ProyectoAnalitico_UPLA;
GO
PARÁMETROFUNCIÓN
CREATE LOGINCrea un inicio de sesión en el servidor.
PASSWORDDefine la contraseña de acceso.
CHECK_POLICY = ONAplica las políticas de contraseñas de Windows.
CHECK_EXPIRATION = ONHabilita la caducidad de la contraseña según la política de Windows.
DEFAULT_DATABASEEstablece la base de datos predeterminada del usuario.

iConsideración

SQL Server debe tener habilitado el modo mixto y la cuenta que ejecuta el script debe tener permisos para crear inicios de sesión.

  1. Para comprobar la creación del login ejecuta:
T-SQL
SELECT
    name AS Login,
    type_desc AS Tipo,
    is_disabled AS Deshabilitado,
    default_database_name AS BaseDatos
FROM sys.server_principals
WHERE name = 'analista_upla';

✓Resultado esperado

Una fila para analista_upla, con tipo SQL_LOGIN y estado habilitado.

ACTIVIDAD4

Aplicar el principio de menor privilegio

Teoría + T-SQL

Cada usuario debe recibir únicamente los permisos necesarios para realizar sus funciones. Un usuario que consulta información para reportes no necesita permisos administrativos sobre el servidor.

ROLDESCRIPCIÓNUSO RECOMENDADO
sysadminControl total del servidor.Solo administradores autorizados.
securityadminAdministra inicios de sesión y permisos de servidor.Administración de seguridad especializada.
serveradminConfigura opciones del servidor.Administradores de infraestructura.
processadminAdministra procesos de SQL Server.Funciones administrativas específicas.
setupadminAdministra servidores vinculados y procedimientos de configuración.Casos específicos de administración.
publicRol general asignado a todos los logins.Acceso básico inherente.

!Recomendación

No asignes sysadmin al usuario analista_upla: permitiría controlar por completo la instancia, modificar configuraciones y acceder a información que no corresponde a sus funciones.

ACTIVIDAD4.2

Crear el usuario de base de datos

T-SQL

Un Login permite autenticarse en el servidor; un User es la identidad asociada dentro de una base de datos. Ejecuta:

T-SQL
USE ProyectoAnalitico_UPLA;
GO

CREATE USER analista_upla
FOR LOGIN analista_upla;
GO
ACTIVIDAD4.3

Asignar permisos de lectura

T-SQL
T-SQL
USE ProyectoAnalitico_UPLA;
GO

ALTER ROLE db_datareader
ADD MEMBER analista_upla;
GO

iExplicación

El rol db_datareader permite consultar los datos de las tablas y vistas de usuario. No concede por sí mismo permisos de modificación o eliminación de registros.

ACTIVIDAD4.4

Verificar los permisos asignados

T-SQL
T-SQL
USE ProyectoAnalitico_UPLA;
GO

SELECT
    USER_NAME(rm.member_principal_id) AS Usuario,
    r.name AS RolBaseDatos
FROM sys.database_role_members rm
INNER JOIN sys.database_principals r
    ON rm.role_principal_id = r.principal_id
WHERE USER_NAME(rm.member_principal_id) = 'analista_upla';
GO

✓Resultado esperado

El usuario analista_upla pertenece al rol db_datareader.

ACTIVIDAD4.5

Comprobar que no tiene privilegios de administrador

T-SQL
T-SQL
USE master;
GO

SELECT
    sp.name AS Login,
    sr.name AS RolServidor
FROM sys.server_role_members srm
INNER JOIN sys.server_principals sp
    ON srm.member_principal_id = sp.principal_id
INNER JOIN sys.server_principals sr
    ON srm.role_principal_id = sr.principal_id
WHERE sp.name = 'analista_upla';
GO

iCómo leer el resultado

No deben aparecer roles administrativos de servidor. La ausencia de filas no significa que el login carezca de todos los permisos: conserva los del rol public y los concedidos explícitamente.

ACTIVIDAD5

Desactivar cuentas predeterminadas de alto riesgo (sa)

SSMS / T-SQL

La cuenta sa es el inicio de sesión integrado de SQL Server y tiene privilegios administrativos de máximo nivel.

  1. Abre SSMS.
  2. Expande Security > Logins.
  3. Localiza la cuenta sa.
  4. Clic derecho y selecciona Properties.
  1. Revisa el estado de la cuenta.
  2. Si no es necesaria, deshabilítala desde Status seleccionando Disabled.
  3. También puede hacerse con T-SQL:
T-SQL
USE master;
GO

ALTER LOGIN sa DISABLE;
GO

-- Verificar el estado:
SELECT
    name,
    is_disabled
FROM sys.server_principals
WHERE name = 'sa';
GO

!Precaución administrativa

Antes de deshabilitar sa, comprueba que existe otra cuenta administrativa funcional (preferentemente de Windows) con sysadmin y que hay un procedimiento de recuperación de acceso. Deshabilitar sa no elimina la cuenta ni sus permisos: solo impide iniciar sesión.

✓Resultado esperado

is_disabled = 1 indica que la cuenta está deshabilitada.
